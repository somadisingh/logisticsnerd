Prefix logistics-owned physical names if core introduces a name collision. Use core-compatible integer identifiers after mapping approval; standalone string IDs are fixtures only.

The three extra logical tables make inventory ownership, reservations and durable operation results explicit. Ten tables includes the two reused legacy concepts and the still-unbuilt shared item concept; it is not ten migrations or permission to invent shared core. No inbound allocation table is needed in this v1 because each PO explicitly belongs to one demand line. No ledger or stock movement reversal system is invented.

## Database integrity proposal

Every new company-owned row has non-null `business_id` and references `businesses(id)`. Every linked company-owned parent exposes a candidate key `(business_id,id)`. Children use composite foreign keys, never a bare globally valid ID as isolation. The PO additionally references the quote's line as above; reservation references the line's item. If the chosen core identity is generic CRM `entities`, require a verified typed mapping of `(business_id,entity_key,record_id)`; current JSON links are insufficient for these relational guarantees. Confirm referential behavior for delete/archive with core; v1 must restrict deletion of referenced operational facts.

Also constrain enum states, integer quantities/money, nonnegative balances, PO received time/state consistency and order fulfilled time/state consistency. Quotes and approved PO commercial terms must be immutable through all write paths. If snapshot JSON is chosen, canonicalize/version it; snapshot supplier, capacity, quantity priced, price kind/amount, currency, delivery, source and validity, plus agreed purchased quantity/cost. Cache deletion or quote expiry after approval must never alter a PO. Currency is configured once per company for v1; orders/quotes/POs must match it, and immutable operational currency cannot be changed by editing settings.

Cross-row stock sums, line budgets and remaining shortages require concurrency-safe transactions; a row `CHECK` cannot enforce a reservation sum over other rows. Lock affected stock/demand/PO rows in deterministic item order, or use the verified SQLite `BEGIN IMMEDIATE` pattern on the same connection after engine/adapter approval. Read authoritative stock, validate, mutate reservations/on-hand/PO or fulfillment state, and write durable operation result **in one commit**. Unique durable event keys and conditional transitions are required in addition to `received_at`/`fulfilled_at`. A failure rolls everything back; a successful replay returns the stored original result. Locking in the in-memory test adapter is not evidence of database concurrency correctness. See [separate wider core migration dependencies](core-migration-dependencies.md) before drafting a migration.

## Quantities and money

- Original demand never changes. Duplicate item lines combine quantities in first-seen item order only when deadline, priority and aggregate purchase budget are identical. The equal budget is retained once, not added; conflicting constraints are rejected. If callers mean separate per-line allowances, normalize them explicitly before this contract or reject them.
- Available stock = on-hand minus reservations belonging to unfinished orders. First reservation captures `original_shortage`; later physical shortage is `demand - active reservation`. Reservation actions allocate at most physical availability and remaining unallocated shortage, leaving inbound demand assignments intact.
- `quantity_to_purchase` is a **derived view**, not a stale stored counter: `demand - active reservation - approved unreceived PO quantities assigned to this line`. A received PO contributes through reserved stock, never inbound again. A fulfilled line has zero remaining demand, despite releasing its reservations.
- The line budget caps **all approved purchases for that line's shortages**, including already received purchases. Existing stock has no purchase cost in this v1 budget. Compare the combined new and already approved total, using integer cents and one configured currency, with no exchange conversion or invented tax/shipping accounting. Quote prices must include all agreed charges; explicit per-unit linear pricing is distinct from a total priced exact lot. No total-price prorating.
- Capacity, quantity priced and purchased quantity are different facts. Unit quotes cover quantities up to `min(capacity,quantity_priced)`; exact-total quotes cover exactly the priced lot within capacity. Each immutable supplier/line quote can be purchased once. Expiry, current delivery-date freshness and deadline apply at approval; v1 uses UTC calendar dates and permits same-day delivery. After approval, receiving uses frozen terms even if the estimate expires or delivery is late.
- Recommendations are deterministic suggestions only. Source `synthetic` or `ai_estimate` denotes an estimate, not a supplier commitment. The local approval demo uses these fictional facts; production acceptance of estimates as purchase terms requires an explicit product decision and real confirmation path.

## Lifecycle

Order: create → open; reserve/receive recomputes open or ready; ready → fulfilled only for the entire order. PO: explicit owner approval → approved; full receive → received. Approval never changes on-hand or reservations. Receipt adds the full PO quantity once and reserves it for that PO's demand atomically. Only receiving enough for every line makes the order ready; receiving one supplier does not complete another PO. Fulfillment consumes every line's reserved stock and releases reservations together, preserving other orders' stock. Completion timestamps start null and are assigned only on completion.

Partial receipts/shipments, returns, cancellations, transfers, order amendments, quote replacement and undo are unsupported; reject them explicitly. Do not implement these actions by rewriting completion timestamps or using configuration revert.
